## 1. Педагогічна модель (застосовується з фази 4, задокументована зараз)

### Центральна модель: наскрізна логіка мислення

Курс (і М1 зокрема) будується не як послідовність ізольованих тем Python, а як поступове формування **computational thinking** через одну наскрізну ментальну модель:

```text
задача → інформація → дані → перетворення → організація логіки → збереження та взаємодія → система
```

Студент не просто послідовно вивчає `if`, `list`, `function`, `JSON` тощо — на кожному етапі він отримує новий інструмент для побудови дедалі складнішої системи. **Важливо:** це не вимога одного наскрізного проєкту на весь модуль — це одна наскрізна модель мислення, яку демонструють на різних задачах на різних етапах. Конкретне застосування цієї моделі до М1 — у `module_1_audit.md`, розділ «Зафіксована концепція М1».

### 1.1 Аудит наявного матеріалу (замість простого keep/rewrite/retire)

Перед тим як переносити чи переписувати будь-який урок, заповнюємо для нього таблицю:

| Поле | Приклад — «Функції» |
|---|---|
| Результат навчання | Студент розділяє задачу на функції з аргументами й результатом |
| Передумови | Умови, цикли, колекції |
| Типове нерозуміння | Плутає `print()` і `return` |
| Наявний матеріал | Пояснення, notebook, домашнє завдання |

| Повторне застосування | Використовує функцію в обробці файлу через кілька уроків |

Це дозволяє зберегти сильні матеріали й переписувати конкретні слабкі місця, а не переписувати все підряд.

#### Правило мапінгу: за результатом навчання, не за ключовим словом

Додано після аудитів М2–М4 (2026-09-21), коли стало видно, як багато реального контенту зненацька випливає в кожному наступному модулі — і як легко піддатись спокусі одразу «пристроїти» його кудись за поверхневою ознакою. **Ніколи не мапити контент на v5.0-позицію лише за технологією/ключовим словом у файлі.** `generator`/`yield` у notebook не означає автоматично «урок Generators». `datetime` не означає «урок datetime». `Redis` у `module_4/` не означає «Web». `asyncio` не означає, що матеріал підходить саме для вступної asyncio-позиції. Спершу — яку проблему студент тут навчається розв'язувати (Результат навчання з таблиці вище), і лише потім — де в v5.0-сітці це має жити. Одиниця аналізу для будь-якого міжмодульного зіставлення — **learning outcome**, файли — лише джерела під нього, а не навпаки. Див. `cross_module_decision_map.md` як приклад застосування цього правила.

Ще одне пов'язане правило, з практики позицій 13/14 М1 (2026-09-21): коли на одну позицію претендують два незалежних, обидва якісних конспекти (наприклад, старий аудит-схвалений і новіший, переписаний з live-coding-чернетки), **основний обирається за якістю структури й пояснення, не за походженням джерела**. «Старіший» чи «раніше аудит-схвалений» — не аргумент сам по собі. Той, що програв порівняння, не відкидається — стає джерелом для заповнення конкретних прогалин основного.

Пов'язане правило того самого походження: **міграція не повинна випереджати архітектуру.** Коли аудит кількох модулів підряд накопичує прогалини й спірний контент (наприклад, цілий алгоритмічний трек, що фізично лежить у папці «Бази даних» лише з історичних причин, або ~290 клітинок мережевого/конкурентного матеріалу без жодної цільової позиції), правильний крок — зупинитись і звести одну карту рішень (KEEP/SPLIT/MOVE/REWRITE/CREATE/DROP по кожному кластеру), а не одразу переписувати/переносити/дописувати контент по одному аудиту за раз. Так само не варто генерувати контент «під позицію» лише тому, що вона порожня — порожній модуль (напр. М4: 13 з 17 позицій без джерела) потребує окремого проєктування як системи, це вже не міграція, а розробка курсу з нуля.

### 1.2 Модель побудови уроку — стандартизований цикл (спочатку — на двох пілотних уроках, не одразу на всіх 46)

Замість окремого списку прийомів — один стандартизований цикл, який проходить кожен урок:

```text
RETRIEVE → CONCEPT → PREDICT → RUN → INVESTIGATE → MODIFY → CREATE → TRANSFER
```

Це **замінює** будь-яку механічну вимогу на кшталт «10 тестових питань на урок» — стандарт це сам цикл, а не фіксована кількість запитань.

- **RETRIEVE** — відтворення з пам'яті + розподілена в часі практика: кілька коротких завдань із попередніх тем без підглядання на початку уроку, потім розбір помилок; повертатися до тем варто і пізніше, а не лише одразу після пояснення.
- **CONCEPT** — власне новий матеріал: мінімум, потрібний для наступних кроків.
- **PREDICT → RUN → INVESTIGATE → MODIFY → CREATE** — це **PRIMM** (Predict → Run → Investigate → Modify → Make): спочатку читання й розуміння готового коду, потім самостійне написання. Приклад для «Функцій»: передбачити результат готової функції → запустити й пояснити розбіжність із прогнозом → простежити аргументи, локальні змінні й `return` → додати обробку порожнього списку → написати власну функцію для іншої задачі. Усередині цього блоку діє й **поступове зменшення підказок**: розібраний приклад → доповнення пропусків → зміна вимог → самостійна задача — реалізується на наявних прикладах, без переписування всього заново.
- **TRANSFER** — перевірка перенесення навички: після прикладу з оцінками — задача з температурами чи замовленнями. Структура рішення схожа, дані інші — це перевіряє розуміння, а не пере-написання побаченого.

Це підхід, який ми пропонуємо застосувати й перевірити на пілотних уроках — не єдина доведена методика викладання, а конкретне, дослідницьки обґрунтоване рішення для цього курсу.

#### Практикуми: just-in-time theory, не «нуль теорії»

Зафіксовано під час розгляду М1-практикумів П1–П3 (2026-09-21), але правило загальне для будь-якого практикуму в курсі. Номер практикуму не означає, що весь новий матеріал вперше пояснюється саме там, але й не означає, що практикум обходиться взагалі без нового поняття — якщо в сітці 1–7 немає окремої «Урок»-позиції під потрібну теорію, практикум сам стає єдиним місцем, де вона вводиться. Правило: CONCEPT усередині практикуму **дозволений і потрібний**, але лише як **just-in-time theory** — рівно стільки нового поняття, скільки потрібно для наступної дії студента, вбудоване в той самий RETRIEVE→…→TRANSFER цикл (§1.2 вище), а не окрема мінілекція перед практикою. Теорія служить практиці, практика не додається «після» теорії.

**Приклад застосування — алгоритмічна трійка П1→П2→П3 в М1** (повне обґрунтування й вирішені відкриті питання — `module_1_audit.md`, розділ «Архітектура алгоритмічної трійки»): це не три незалежні набори задач з алгоритмів, а одна навчальна дуга.

```text
              ALGORITHMIC THINKING
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼

       П1            П2          П3
    EVALUATE        CHOOSE     REPRESENT

   complexity      strategy    data structure
       │              │            │
       └──────────────┼────────────┘
                      ▼
             TRADE-OFF THINKING
```

```text
П1 — EVALUATE
"Наскільки дороге моє рішення?"

        ↓

П2 — CHOOSE
"Яку властивість даних
я можу використати?"

        ↓

П3 — REPRESENT
"Чи можу я змінити представлення даних,
щоб отримати кращий алгоритм?"
```

### 1.3 Політика використання AI (у кожному модулі, не лише в бонусному треку)

- **Режим самостійної перевірки**: коротке завдання без AI — пояснити код, знайти помилку.
- **Режим роботи з AI**: студент може отримувати підказки й варіанти рішення від AI, але перевіряє результат тестами, пояснює його та адаптує під нову вимогу.
- У домашніх роботах — коротка примітка: де використав AI, що перевірив, що виправив. Оцінюється і працездатність рішення, і здатність студента його пояснити.

### 1.4 Git/GitHub — паралельний горизонтальний трек (не відкладається до позиції 15)

Git/GitHub — це не окрема тема, яку викладають один раз, а **горизонтальний трек**, що йде поруч із вивченням Python з першого заняття, бо Pull Request — цільовий спосіб здачі домашніх робіт. `docs/00_getting_started/` — канонічне джерело практичних інструкцій (SSH, fork/clone, workflow) — воно не переказується в уроках повторно.

Прогресивне засвоєння:

```text
L1          побачив workflow
 ↓
HW1         перша спроба
 ↓
HW2–HW...   повторює в реальній роботі
 ↓
L15         розуміє внутрішню модель Git
 ↓
L17         використовує як нормальний workflow
```

Повторення Git протягом М1 — **навмисна практика (spaced practice), не дублювання**.

На L1 студент отримує лише мінімальну робочу модель, у перехідному режимі: workflow рекомендується починати якомога раніше, але він не повинен ставати бар'єром, що заважає вчити Python у перші заняття:

```text
GitHub account
      ↓
SSH / access
      ↓
clone / pull
      ↓
виконати homework
      ↓
commit
      ↓
push
      ↓
Pull Request
```

Принцип для студентів: чим раніше починаєш здавати домашні роботи через GitHub і Pull Request, тим більше реальної практики Git отримуєш і тим швидше workflow стає звичайним робочим інструментом.

**L15 змінює функцію.** Це вже не «перший Git/GitHub» — студент ним уже користується. Тут відбувається перехід від «Git як інструмент» («я знаю, які команди виконувати») до «Git як система» («я розумію, що насправді відбувається»):

```text
working tree → staging area → local repository → commit graph → branches → remote → push / pull → merge → Pull Request
```

Плюс: конфлікти, `.gitignore`, хороші commits, README, структура repository, базове представлення навчальних проєктів (мінімальна професійна база — не personal-branding урок: зрозумілий README, адекватна структура, `.gitignore`, dependencies, нормальна commit history, кілька проєктів на показ).

Робоча назва L15: **«Git & GitHub: від використання workflow до розуміння системи»**.
