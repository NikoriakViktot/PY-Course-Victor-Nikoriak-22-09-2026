## Як читати карту рішень

```text
                    v5.0 COURSE
                         │
        ┌────────────────┼────────────────┐
        │                │                │
   REQUIRED           EXISTING         MISSING
   CONCEPTS           SOURCES           CONTENT
        │                │                │
        └──────────► DECISION ◄───────────┘
                         │
              KEEP / SPLIT / MOVE /
              REWRITE / CREATE / DROP
```

Кожен вузол нижче — картка одного результату навчання:

```text
LEARNING OUTCOME
"..."
        │
        ├── v5.0 target: ...
        ├── sources: ...
        ├── source quality: ...
        ├── action: ...
        └── missing: ...
```

Картки даються повністю там, де є реальне рішення. Там, де аудит уже дав однозначний, безспірний висновок (один якісний файл, чіткий збіг, дія «Зберегти» без відкритого питання) — це компресовано в один рядок таблиці §4, щоб не дублювати аудити.

## 1. Чотири вузлові рішення

Це те, що варто пройти разом першим — вони або зачіпають кілька модулів одразу, або мають реальну ціну помилки, якщо вирішити їх мовчки/автоматично.

### 1.1 Algorithms track — стара структура репо вже не відповідає новій концептуальній структурі курсу

`module_3/` називається «Бази даних», але фізично містить старі уроки 22–28 (Big O, deque/queue, зв'язний список, пошук/хешування, дерева, сортування, графи) — це не М3, це банк джерел для практикумів П1–П6 у М1/М2. Директорія `module_3/` — історична назва зі старого репо, не семантичний контейнер v5.0.

```text
LEARNING OUTCOME
"Студент оцінює ефективність рішення через нотацію Big O"
        │
        ├── v5.0 target: M1 / П1 (позиція 8)
        ├── sources: module_3/lessons/lesson_22_big_O (лекція + big_o_taxi_lab/)
        ├── source quality: сильна теорія, практикум (FizzBuzz/паліндром/Caesar) відсутній повністю
        └── action: KEEP (теорія як інструкторська довідка) + CREATE (самі задачі практикуму)

LEARNING OUTCOME
"Студент обирає стратегію пошуку (linear/binary/two-pointer/sliding-window)"
        │
        ├── v5.0 target: M1 / П2 (позиція 11)
        ├── sources: module_3/lessons/lesson_25_search_hashing, частини 1–4
        ├── source quality: сильна теорія пошуку; sliding-window задач немає
        └── action: KEEP (теорія) + CREATE (задачі); НЕ різати файл — уже вирішено в M1-аудиті

        └── action: KEEP (теорія) + CREATE (задачі) — той самий файл, що й П2 вище, свідомо НЕ розрізається

LEARNING OUTCOME
"Студент пише рекурсивні функції з базовим випадком, застосовує divide & conquer / backtracking"

        └── action: CREATE (теорія + задачі), з lesson_23 як частковою відправною точкою

LEARNING OUTCOME
"Студент розпізнає задачі під DP (перекриття підзадач), пише memoization/tabulation, відрізняє DP від greedy"
        │
        ├── v5.0 target: M2 / П5 (позиція 26)
        ├── sources: немає жодного
        └── action: CREATE — повністю з нуля; кандидат на парну конструкцію з П4 (рекурсія → мемоізація → tabulation), за зразком L6→L7 (звіт кафе → функції) у М1

LEARNING OUTCOME
"Студент реалізує stack/queue/heap/trie/LRU cache і синтезує їх у ООП-пакет (артефакт М2)"
        │
        ├── v5.0 target: M2 / П6 (позиція 28)
        ├── sources: module_3/lesson_23_deque_queue (stack/queue), lesson_24_list_data_structure
        │             ("Завдання 3 — LRU Cache" — майже готове); heap і trie — джерел немає

        │             має сильного кандидата: module_2/lesson_21_module2_review (ecommerce_analytics/)
        └── action: SPLIT (розібрати lesson_23/24 по структурах) + CREATE (heap, trie, з нуля) +
                    DECIDE (чи ecommerce_analytics — прообраз артефакту, чи інший кейс з нуля)
```

**Без цільової позиції в поточній xlsx-сітці взагалі** (не тягнути мовчки, не форсувати в жодну з наведених вище):

- `lesson_26_trees` (дерева) — повний готовий матеріал, жоден з П1–П6 не називається «дерева»
- `lesson_27_sorting` (сортування) — повний готовий матеріал, найближче дотично до Big O (П1), але сортування там не назване
- `lesson_28_graphs` (графи, BFS/DFS/Dijkstra) + `docs_Neo4j.md` — Neo4j-частина концептуально ближча до М3 (Бази даних), але не названа в xlsx для позицій 29–30

**Рішення, яке потрібне тут:** чи практикуми П1–П6 в xlsx описані вичерпно (і дерева/сортування/графи/Neo4j — свідомо поза обов'язковою програмою, зберігаються як факультативний банк), чи навігаційна таблиця сама неповна і потребує уточнення. Це рішення про **зміст програми**, не про розташування файлів — тому саме воно, не директорія `module_3/`, має визначати, куди що йде.

**Побічна знахідка, що підтверджує саму тезу цього пункту:** `module_3/docker_guide.md` і супутній HTML — повноцінний посібник з Docker, за темою це v5.0 М5 позиція 48, не «Бази даних», і взагалі `migration_plan.md` §0 вирішив поки не переносити DevOps-контент старого `module_5`. Файл фізично опинився не там, де мав бути, за тією ж логікою, що й увесь алгоритмічний трек, — directory ≠ semantics, послідовно.

### 1.2 Networking/concurrency block — цінний матеріал без домівки

```text
LEARNING OUTCOME
"Студент розрізняє threading/multiprocessing/asyncio, розуміє GIL на базовому рівні,
пише простий async def"
        │
        ├── v5.0 target: M2 / позиція 27 ("...вступ", 4 год)
        ├── sources: module_4/lessons/lesson_30_networking_base, lesson_32_threading_concurrency,
        │             lesson_33_multiprocessing, lesson_34_asyncio — ≈290 клітинок сукупно
        ├── source quality: глибокий, вже v5.0-стилізований (Learning Objectives, рівні складності,
        │             рефлексія) — але обсяг на порядок перевищує одну вступну позицію
        └── action: ADVANCED_TRACK_CANDIDATE — HOLD
```

Не стискати механічно до одного вступного заняття (втратить майже все, що в ньому цінного), і не видаляти. Позначено `HOLD` до окремого рішення: (а) self-paced advanced-блок поза сіткою, за зразком AI-бонус-треку; (б) джерело для майбутнього окремого модуля; (в) щось третє. Це рішення одночасно зачіпає М2-аудит (позиція 27 позначена тим самим питанням) і М4-аудит (файли фізично лежать у `module_4/`, хоча тема — не Web).

### 1.3 М4 Web — 13 з 17 позицій без джерела: це розробка курсу, не міграція

Реальний, готовий до використання матеріал є **тільки для позиції 31** (HTTP/requests). Позиція 32 має один фрагмент-підрозділ. Позиції 33–38, 40–47 — **Django, DRF, FastAPI CRUD, auth, testing, AI/LLM-інтеграція, архітектура застосунків, WebSockets, security advanced, Telegram Bot — не мають у репозиторії жодного джерела взагалі.**

Це не питання «звідки взяти файл» — старого `module_5`-бандла (Django/DevOps), на який міг би розраховувати цей блок, у новому репо просто немає. Тому **дія тут не CREATE по одній позиції за раз** — 13 позицій, згенерованих незалежно одна від одної без спільного дизайну, дадуть модуль без внутрішньої логіки (чому саме такий порядок тем, що є наскрізним прикладом, де фейдинг scaffolds). Перед тим як писати хоч один урок цього блоку, М4 потребує окремого проєктування як системи — тієї самої роботи, яку M1-аудит уже проробив для свого модуля (центральна модель мислення + наскрізний приклад + AI-політика), тільки з нуля, без старого матеріалу як опори.

**Явна заборона:** не генерувати заглушки-уроки просто щоб заповнити порожні позиції. Порожній модуль спершу проєктується, потім наповнюється — не навпаки.

### 1.4 Redis — приклад того, чому directory ≠ semantics

```text
LEARNING OUTCOME
"Студент розуміє Redis як key-value/in-memory сховище, базові структури даних,
типові сценарії (кеш, сесії, pub/sub)"
        │
        ├── v5.0 target: M3 / позиція 30 ("Redis overview")
        ├── OR v5.0 target: M4 / позиція 39 ("Middlewares і кешування — Redis на практиці")
        ├── sources: module_4/lessons/lesson_30_networking_base/Redis_docs.md, redis_socket_lesson/
        ├── source quality: реальний контент існує, але фізично лежить у М4-папці,
        │             хоча номер «30» у старій назві натякає на позицію М3
        └── action: DECIDE — куди, і чи по частинах (overview → M3/30, практика на web-рівні → M4/39)
```

У `module_3/` (яка мала б бути «Базами даних») Redis-контенту немає взагалі — жоден з трьох аудитів (М2/М3/М4) сам по собі не мав підстав це вирішити, кожен побачив лише свій шматок. Це і є найчистіший приклад із усього циклу аудитів: фізичне розташування файлу («лежить у `module_4/`») підказувало б «це Web», але концептуально контент — про сховище стану, і однаково правдоподібно належить М3. **Ніколи не довіряти директорії як джерелу істини про призначення контенту** — саме цей випадок і привів до формалізації правила в `migration_plan.md` §1.1.

## 5. Restaurant-family — свідомо не займано в цьому документі

`restaurant_analysis.ipynb`, `restoran_beginner.ipynb`, `restoran_tips.ipynb`, `restoran_v4.ipynb` — один датасет, прогресія підходів (beginner solution → кращі структури даних → функції/декомпозиція → генератори/стрімінг → повний аналіз). За інструкторським рішенням (2026-09-21) це розглядається пізніше як **один педагогічний артефакт**, що демонструє еволюцію рішення з ростом знань студента — не як чотири файли, які треба розкидати по позиціях М1/М2/М3 за технікою, яку кожен з них використовує (що прямо суперечило б правилу «мапити за результатом навчання, не за ключовим словом» із §1.1 `migration_plan.md`). Жодних дій із цими файлами в цьому документі не пропонується.
