    Урок 13. Виключення¶

    Передумови: уроки 3–12 (типи даних, умови, функції, списки/словники, доступ до елементів). Розв'язує: перехід від коду, що аварійно зупиняється на будь-якій неочікуваній вхідній умові, до коду, який контрольовано розпізнає й обробляє помилки.

    RETRIEVE¶

    На початку — коротке пригадування без підглядання: що повертає функція без return; чим d.get("x", 0) відрізняється від d["x"], коли ключа немає; чому умову з двома межами краще писати одним if ... or ..., а не двома окремими if.

    CONCEPT¶

    Дві категорії помилок¶

    Перш ніж розбирати конкретні винятки, варто розрізняти два принципово різні моменти, коли Python може відмовити виконувати код.

    SyntaxError виникає ще до запуску програми — на етапі читання коду. Якщо десь забута дужка чи двокрапка, інтерпретатор не зможе навіть почати виконання: жоден рядок, включно з print() до помилки, не встигне відпрацювати.

    Помилки часу виконання (runtime errors, вони ж винятки) — це синтаксично коректний код, який стартує нормально, але натрапляє на неможливу операцію під час роботи: ділення на нуль, звернення до відсутнього ключа словника, відкриття неіснуючого файлу. Частина програми до цього моменту встигає виконатись — і саме це відрізняє runtime-помилку від SyntaxError.

    SyntaxError Runtime Error
    Коли виникає при читанні коду під час виконання
    Чи стартує програма ні так, падає пізніше
    Приклад забута : або ( 1 / 0, int("abc")

    Далі йдеться саме про другу категорію.

    Виняток як контрольований збій¶

    Коли виникає runtime-помилка, Python не просто «падає» — він створює об'єкт винятку (exception) і зупиняє звичайний потік виконання:

    рядок 1 ✓ → рядок 2 ✓ → рядок 3 💥 ВИНЯТОК
                              │
                Python шукає найближчий except,
                що збігається з типом винятку,
                піднімаючись вгору по стеку викликів
                              │
        знайшов → перехопив і обробив
        не знайшов → програма завершується, Traceback у термінал

    Шість основних вбудованих винятків¶

    Виняток Коли виникає Приклад
    ValueError правильний тип, але некоректне значення int("привіт")
    TypeError несумісні типи в операції "ціна: " + 5
    ZeroDivisionError ділення на нуль 10 / 0
    IndexError індекс за межами списку [1, 2, 3][99]
    KeyError ключ відсутній у словнику {"name": "Alice"}["age"]
    FileNotFoundError файл не знайдено open("ghost.txt")

    try / except / else / finally¶

    try огортає ризиковий код; якщо всередині станеться виняток заданого типу, виконання переходить у відповідний except, а не зупиняє програму:

    def get_safe_price(raw_price):
    try:
        return float(raw_price)
    except ValueError:
        print("❌ Помилка: введіть числове значення!")
        return None

    else виконується тільки якщо try пройшов без винятку — це місце для коду, який має запускатись лише після успіху, без ризику, що його власна помилка «змішається» з тими, що обробляються в except. finally виконується завжди, незалежно від результату — типове місце для логування чи закриття ресурсів:

    try:
    amount = float(amount_str)
    tax = 100 / amount
except ValueError:
    print("❌ Це не число!")
except ZeroDivisionError:
    print("❌ Сума не може бути нулем!")
else:
    print(f"✅ Податок розраховано: {tax:.2f}%")
finally:
    print("📡 Лог: спроба транзакції зафіксована.")

    Порядок правил: except-блоки перевіряються згори донизу, спрацьовує перший збіг типу — тому специфічні типи мають стояти вище загальних; finally виконується завжди, навіть якщо в try є return.

    Антипатерн «підгузок»¶

    Голий except: (без вказання типу) ловить абсолютно все — не лише очікувану проблему вводу, а й власні баги програміста:

    try:
    number = int("10")
    print(numbor)          # опечатка: має бути number
except:                    # ловить усе, включно з NameError від опечатки
    print("Щось пішло не так...")

    Повідомлення тут бреше: конвертація пройшла успішно, впав зовсім інший рядок через опечатку — але голий except приховав справжню причину. Правило: вказуй конкретний тип винятку, який ти очікуєш і знаєш, як обробити.

    raise — генеруємо винятки самі¶

    Дані можуть бути технічно коректними (справжній float), але логічно неприпустимими для бізнес-правила — знижка 150%? Python цього сам не знає, але ми знаємо:

    def set_discount(percent: float):
    if percent < 0 or percent > 100:
        raise ValueError(f"Знижка {percent}% неможлива (має бути від 0 до 100)")

    Stack unwinding¶

    Якщо функція не перехоплює помилку сама, виняток піднімається вгору по стеку викликів до першої функції, яка має відповідний except:

    function_a()  ← тут є try/except
    └── function_b()  ← немає обробки
            └── function_c()  ← ZeroDivisionError тут

    try/except не потрібен у кожній функції — обробник ставлять там, де відомо, що саме відповісти на помилку, а не обов'язково там, де вона сталася.

    EAFP проти LBYL¶

    LBYL (Look Before You Leap, стиль C/Java) — перевіряй умову перед дією:

    if os.path.exists(filename) and os.access(filename, os.R_OK):
    with open(filename) as f:
        content = f.read()

    Проблема: між перевіркою і відкриттям файл теоретично може зникнути (race condition).

    EAFP (Easier to Ask Forgiveness than Permission, стиль Python) — просто пробуй, а на помилку реагуй:

    try:
    with open(filename) as f:
        content = f.read()
except FileNotFoundError:
    print("Файл не знайдено")

    Python явно рекомендує EAFP — вікна для race condition немає, а try без винятку практично безкоштовний.
